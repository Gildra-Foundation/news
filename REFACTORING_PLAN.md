# План модульной переработки GildraNews

## Репозитории

- Основной рабочий репозиторий: `https://github.com/Gildra-Foundation/news` (`origin`).
- Исходный проект, использованный как база: `https://github.com/Zulut30/newslatter-bot` (`upstream`).
- Новые изменения должны отправляться только в `origin`; `upstream` используется для сравнения и получения обновлений исходного проекта.

## 1. Цель переработки

Превратить текущий работающий прототип в понятное Python-приложение, где сбор новостей, обработка текста, перевод, инфографика, хранение и публикация разделены и могут изменяться независимо.

Главное требование: сначала сохранить текущее поведение, затем подключить качественные редактор и переводчик через ChatGPT Server с рабочей сессией и моделью GPT-5.6 Luna.

## 2. Что сейчас требует улучшения

- Все Python-модули находятся в корне проекта.
- `main.py` содержит около 900 строк и совмещает запуск приложения, Telegram-команды, обработку ссылок, черновики, расписание и real-time события.
- `ai.py` совмещает фильтрацию, рерайт, перевод, GitHub-сводки и дайджесты и напрямую зависит от Gemini.
- `db.py` совмещает схему, миграции, соединение и запросы всех сущностей.
- Бизнес-процесс напрямую импортирует Telegram, Gemini, SQLite и Pillow, поэтому компоненты трудно заменять и тестировать отдельно.
- Автоматических тестов нет; безопасная перестройка структуры ничем не защищена от регрессий.
- Сборка Docker вручную перечисляет каждый Python-файл и будет ломаться при любом переносе.

## 3. Архитектурные правила

1. Бизнес-логика не импортирует aiogram, Telethon, SQLite, Pillow или клиент конкретной AI-модели.
2. Внешние системы подключаются через интерфейсы: `NewsSource`, `TextEditor`, `Translator`, `ImageGenerator`, `Publisher` и репозитории.
3. GPT-5.6 Luna является конфигурацией адаптера ChatGPT Server, а не зависимостью доменной логики.
4. Секреты и файлы сессий остаются вне Git и передаются через переменные окружения или защищённый volume.
5. Каждый этап миграции сохраняет запускаемое приложение и имеет тест или smoke-проверку.
6. Новая функция добавляется в соответствующий модуль, а не в `main.py`.

Направление зависимостей:

```text
Telegram handlers / scheduler
            ↓
     application use cases
            ↓
      domain + interfaces
            ↑
AI / SQLite / Telegram / rendering adapters
```

## 6. Порядок реализации

### Этап 0. Зафиксировать текущее поведение

**Задача:** создать минимальную страховочную сетку до перемещения кода.

**Критерии готовности:**

- Добавлены тесты форматирования Telegram-поста, нормализации источника, дедупликации и разбора ответа AI.
- Есть smoke-тест загрузки конфигурации с тестовыми переменными окружения.
- Текущее приложение по-прежнему запускается прежней командой.

**Проверка:** `pytest` и компиляция всех Python-модулей.

### Этап 1. Создать Python-пакет и единый вход

**Задача:** добавить `pyproject.toml`, каталог `src/gildranews` и команду запуска `python -m gildranews`, пока оставив совместимые обёртки для старых модулей.

**Критерии готовности:**

- Проект устанавливается как пакет.
- Импорты используют имя `gildranews`, а не файлы из текущего каталога.
- Docker копирует пакет целиком и запускает модуль, а не вручную перечисленные файлы.

**Проверка:** сборка контейнера и запуск команды с тестовой конфигурацией.

### Этап 2. Выделить модели и контракты

**Задача:** перенести `FetchedPost`, `ExternalPost`, `Rewrite`, `FilterResult`, `ProcessResult` и черновик в доменные модели; определить асинхронные интерфейсы внешних компонентов.

Минимальные контракты:

- `NewsSource.fetch(...) -> list[NewsItem]`
- `NewsFilter.evaluate(...) -> FilterDecision`
- `Translator.translate(...) -> TranslatedText`
- `TextEditor.edit(...) -> EditedArticle`
- `ImageGenerator.create(...) -> VisualAsset`
- `Publisher.publish(...) -> PublishedPost`
- `DraftRepository` и `PublicationRepository`

**Критерии готовности:**

- Доменные модели не импортируют внешние SDK.
- Use case обработки новости принимает зависимости через конструктор.
- Существующие реализации подключаются через адаптеры без изменения результата.

**Проверка:** unit-тест полного use case с fake-компонентами, без сети и Telegram.

### Этап 3. Разделить базу данных

**Задача:** отделить управление SQLite, миграции и репозитории источников, публикаций, черновиков и запусков.

**Критерии готовности:**

- SQL-схема версионируется миграциями.
- Application-слой не видит `aiosqlite` и SQL-запросы.
- Текущая `data/newsbot.db` открывается без потери данных.

**Проверка:** integration-тест миграции копии старой БД и CRUD каждого репозитория.

### Этап 4. Разнести входы и выходы

**Задача:** оформить Telegram, внешние сайты, публикацию, рендер карточек и emoji как отдельные адаптеры.

**Критерии готовности:**

- Telegram-reader и внешние HTTP-источники возвращают единую модель `NewsItem`.
- Публикация получает уже готовый `Article`, не знает о переводчике или БД.
- Рендерер получает типизированное описание визуала и возвращает файл/байты с явным жизненным циклом.

**Проверка:** unit-тесты преобразования данных и integration-тест HTTP через mock-сервер.

### Этап 5. Разделить Telegram-интерфейс и запуск приложения

**Задача:** сократить `main.py` до composition root: загрузить config, создать зависимости, зарегистрировать роутеры, запустить scheduler и корректно закрыть ресурсы.

**Критерии готовности:**

- Команды администратора, источники, черновики и callback-кнопки находятся в отдельных router-модулях.
- Авторизация администратора реализована одной общей зависимостью/middleware.
- Завершение процесса закрывает HTTP-клиенты, БД, Telethon и scheduler.

**Проверка:** тест регистрации роутеров и smoke-запуск/остановка приложения.

### Этап 6. Подключить ChatGPT Server и GPT-5.6 Luna

**Задача:** реализовать адаптер `chatgpt_server.py`, использующий заданную серверную сессию, и подключить его к независимым интерфейсам фильтра, перевода и редактора.

**Критерии готовности:**

- Адрес сервера, идентификатор/настройки сессии, модель `gpt-5.6-luna`, таймауты и число повторов задаются конфигурацией.
- Секреты и данные сессии не попадают в логи, Git или Docker image.
- Ответ модели валидируется по строгой схеме; некорректный ответ не публикуется автоматически.
- Переводчик и редактор можно заменить независимо друг от друга.
- Старый Gemini-адаптер временно доступен как откат до успешной приёмки Luna.

**Проверка:** contract-тест на fake-сервере, один ручной прогон в тестовый Telegram-канал и проверка fallback/error flow.

### Этап 7. Качество и эксплуатация

**Задача:** добавить структурированные логи, метрики этапов конвейера, повторные попытки с ограничениями и понятную документацию запуска.

**Критерии готовности:**

- Для одной новости виден путь: источник → фильтр → перевод → редактура → визуал → публикация.
- Повторный запуск не создаёт дубликат.
- Ошибка AI, сети, рендера или Telegram не обрушает весь процесс и фиксируется без секретов.
- README отражает новую структуру, конфигурацию, команды и восстановление после сбоя.

**Проверка:** `pytest`, lint, type-check, сборка Docker и end-to-end прогон в тестовом канале.

## 7. Контрольные точки

### После этапов 0–2

- Тесты проходят.
- Поведение публикации не изменилось.
- Основной pipeline тестируется без Telegram, SQLite и реального AI.

### После этапов 3–5

- Старая БД совместима.
- Все команды Telegram работают.
- В корне больше нет рабочих `.py`-модулей, кроме временных совместимых обёрток; после проверки они удаляются.

### После этапов 6–7

- GPT-5.6 Luna обрабатывает тестовый поток через ChatGPT Server.
- Есть безопасный откат на старый AI-адаптер.
- Контейнер стабильно проходит полный цикл и готов к длительной работе.

## 8. Definition of Done для каждого этапа

- Изменение небольшое и посвящено одной архитектурной границе.
- Тесты старого и нового поведения проходят.
- Нет секретов, `.env`, Telegram-сессий или рабочих БД в Git.
- Конфигурация и публичные интерфейсы документированы.
- Ошибки содержат полезный контекст, но не содержат исходные секретные данные.
- Проект остаётся запускаемым после каждого этапа.

## 9. Риски и решения

| Риск | Решение |
|---|---|
| Большой перенос ломает импорты | Переносить по одному вертикальному сценарию и временно оставить совместимые обёртки |
| Потеря существующей SQLite-БД | Проверять миграции на копии и сохранять обратную совместимость |
| Неустойчивый формат ответа модели | Строгая схема ответа, валидация, ограниченный retry и запрет автопубликации при ошибке |
| Истечение серверной сессии | Явная диагностика состояния, безопасное обновление сессии и уведомление администратора |
| Дубли при повторных попытках | Идемпотентный ключ источника и атомарная фиксация статуса публикации |
| Смешивание рефакторинга с новой AI-логикой | Сначала структурная миграция с Gemini, затем отдельное подключение ChatGPT Server/Luna |

## 10. Что нужно уточнить перед этапом 6

- Точный протокол ChatGPT Server: HTTP API, CLI/RPC или другой транспорт.
- Как сервер идентифицирует и восстанавливает рабочую сессию.
- Должна ли Luna выполнять фильтрацию, перевод и редактуру одним вызовом или отдельными шагами.
- Какие языки перевода, редакционный стиль и правила проверки фактов обязательны.
- Нужна ли ручная модерация каждого материала или автопубликация разрешена после проверок качества.

Рекомендуемый первый практический шаг — выполнить этап 0, затем этапы 1–2. После этого редактор и переводчик можно будет подключать как отдельные модули без очередного переписывания всего бота.
